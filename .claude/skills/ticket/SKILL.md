# Тикет из бэклога

Аргумент: `$ARGUMENTS` — номер тикета. Если пусто — взять первый тикет в `docs/BACKLOG.md`,
у которого в заголовке нет «ГОТОВО» / «ОТМЕНЕНО» и есть незакрытые пункты `- [ ]`.
Если таких тикетов нет — сказать пользователю, что бэклог пуст, и предложить сформулировать
новый тикет; дальше не идти.

## 1. Понять задачу
- Прочитать раздел тикета в `docs/BACKLOG.md` целиком, включая «**Готово, когда:**» —
  это критерий приёмки.
- Прочитать файлы, которые тикет упоминает, и соседние фичи того же типа как образец
  (новая фича → `src/features/*`, ИИ → контракт в `src/ai/` + реализация в `src/claude/`).
- Если тикет неоднозначен или конфликтует с текущим кодом — задать пользователю
  вопрос до начала реализации.

## 2. Реализовать
- Соблюдать конвенции из `CLAUDE.md`: код на английском, тексты бота и промпты — на
  русском, ответы Claude по еде — только через tool use, время в UTC.
- Меняется схема БД → действовать по скиллу `/migration` (файлы в `drizzle/` руками не
  править — их блокирует хук).
- Новая чистая логика (расчёты, форматирование, разбор) — покрыть vitest-тестом рядом
  с файлом (`*.test.ts`), по образцу существующих тестов.
- Новая команда бота → добавить её в `/help`.

## 3. Проверить
```bash
npm run build && npm test
```
Оба должны пройти. Если падает — чинить, а не отключать тесты. Результат прогона
показать пользователю (кратко: сколько тестов, всё ли зелёное).

## 4. Отметить в бэклоге
В `docs/BACKLOG.md`: пункты тикета `- [ ]` → `- [x]`, к заголовку дописать « — ГОТОВО».
Если по ходу появилось что-то сделанное иначе, чем в тикете, — поправить текст пункта,
чтобы бэклог описывал фактическое состояние.

## 5. Обновить CLAUDE.md
Если появились новые файлы/модули, переменные окружения или команды — внести их в
`CLAUDE.md` (структура кода, стек, «Как запускать»). Мелочи не добавлять.

## 6. Коммит реализации
Коммитить прямо в `master`, без отдельной ветки. Сообщение — в стиле истории репозитория:
```
[N] <кратко по-английски, что сделано>
```
В коммит — все изменения тикета (код, тесты, миграции, `docs/BACKLOG.md`, `CLAUDE.md`).
Не пушить, пока пользователь не попросит.

## 7. Code review и исправление замечаний
- Запустить скилл `code-review` (через Skill tool) на коммит тикета: аргумент — диапазон
  коммитов тикета (например `HEAD~1..HEAD`), уровень `high`.
- Каждое замечание проверить по коду: реальные баги и нарушения конвенций `CLAUDE.md` —
  исправить; ложные срабатывания и спорные мелочи — пропустить, кратко записав почему.
- Если что-то исправлено — снова `npm run build && npm test` (оба зелёные), затем
  отдельный коммит:
  ```
  [N] fix review findings: <кратко по-английски, что поправлено>
  ```
- Если замечаний нет или все отклонены — второй коммит не делать.
- В конце в `git status` не должно остаться незакоммиченных изменений по тикету.

## 8. Итог пользователю
3–6 строк: что сделано, как проверить в боте вручную (какую команду/сообщение
отправить), результат build/test, итоги ревью (сколько замечаний исправлено/отклонено),
хеши коммитов.

## 9. Предложить следующий тикет
Найти в `docs/BACKLOG.md` следующий незакрытый тикет (по тому же правилу, что в начале:
без «ГОТОВО» / «ОТМЕНЕНО», есть `- [ ]`). Коротко описать его (номер, название, суть в
1–2 строки) и спросить, браться ли за него: «Запустить `/ticket M`?». Самому не
начинать. Если бэклог пуст — так и сказать.
